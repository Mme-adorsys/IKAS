```typescript
import { randomUUID } from 'crypto';
import { DiscoveredServer } from '../../types/discovery';
import { Finding } from '../../types/findings';
import { PROMPT_INJECTION_PATTERNS } from '../../data/prompt-injection-patterns';

export function scanPromptInjection(servers: DiscoveredServer[]): Finding[] {
  const findings: Finding[] = [];
  for (const server of servers) {
    for (const tool of server.tools) {
      for (const pattern of PROMPT_INJECTION_PATTERNS) {
        if (pattern.match(tool)) {
          findings.push({
            id: randomUUID(),
            title: `${pattern.name}: ${tool.name}`,
            description:
              `Pattern "${pattern.name}" (${pattern.id}) matched in tool "${tool.name}" on ${server.baseUrl}. ` +
              `Full tool description: ${tool.description ?? '(none)'}`,
            severity: pattern.severity,
            component: `${server.baseUrl}#${tool.name}`,
            score: pattern.score,
            owaspCategory: pattern.owaspCategory,
          });
        }
      }
    }
  }
  return findings;
}
```

Implementation notes:
- Import path uses `../../` (two levels up) because this file lives in `src/stages/static-analysis/` (one deeper than `src/stages/`).
- Use `randomUUID()` from `crypto` for Finding IDs — matches `classifyShadowServers` and `applyCveLookup` conventions exactly.
- Component identifier format: `${baseUrl}#${toolName}` — matches the convention used in test assertions and consistent with `cve-lookup.ts` finding shape for tool-level findings.
- Per D-03, the FULL tool description must appear in `Finding.description`. Do NOT truncate.
- Do NOT deduplicate findings here — if a tool matches multiple patterns, emit one finding per match. Deduplication is Claude's-discretion territory and current scope is "emit all matches" (RESEARCH.md Open Question 3).
- Do NOT add an export for the directory (no barrel file).
- No try/catch needed at this layer — regex predicates do not throw on string input; the orchestrator (Plan 06) will wrap with try/catch.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `DiscoveredServer.tools[].description` → regex engine | Tool descriptions originate from external MCP servers and are attacker-controllable; this is the actual content being analysed |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-05 | Denial of Service | Regex catastrophic backtracking on malicious tool descriptions | mitigate | All regexes in PROMPT_INJECTION_PATTERNS use simple alternation/literal patterns (no nested quantifiers like `(a+)+`). Verified safe by inspection. The base64 pattern `[A-Za-z0-9+/]{40,}={0,2}` is linear. |
| T-03-06 | Prompt Injection (self) | Tool description containing prompt injection becomes embedded in Finding.description | mitigate | Finding.description is treated as data in JSON output; not concatenated into any LLM prompt downstream. If Phase 6 report renderer uses Markdown, special chars are emitted as text content, not template substitution. |
| T-03-07 | Spoofing | Tool with empty/missing name field could produce malformed component identifier | accept | ToolDefinition.name is required (non-optional in interface); discovery stage guarantees name is a string before adding to tools[]. |
| T-03-08 | Information Disclosure | Full tool description in Finding may contain secrets if MCP server leaks them | accept | Out of scope: this is the user's MCP server output. Static analyser merely surfaces what is already exposed. Documented as acceptable. |
</threat_model>
